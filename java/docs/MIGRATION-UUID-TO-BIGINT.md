## Rationale

**Why UUID → BIGINT?**
1. **Performance:** BIGINT (8 bytes) vs UUID (16 bytes) — faster indexing, smaller storage
2. **Readability:** BIGINT IDs shorter, easier to log and debug
3. **Caching:** BIGINT → smaller in-memory caches
4. **Sequences:** GENERATED BY DEFAULT AS IDENTITY simpler than UUID generation

**Metrics:**
- Transaction ID storage: 16 bytes → 8 bytes (50% reduction)
- Index size: ~15M rows × 16 bytes = 240MB → 120MB
- Network payload: UUIDs in JSON responses smaller

## Rollback Plan

**If migration fails:**
1. ROLLBACK PostgreSQL transaction (automatic if any step fails)
2. Keep `coa_trans_old`, `coa_trans_data_old`, `coa_proposal_old` tables
3. Revert Java code to use UUID (if needed)
4. Application continues with UUID IDs

**SQL to restore:**
```sql
-- If tables were already swapped, reverse it
DROP TABLE coa_trans;
DROP TABLE coa_trans_data;
DROP TABLE coa_proposal;
ALTER TABLE coa_trans_old RENAME TO coa_trans;
ALTER TABLE coa_trans_data_old RENAME TO coa_trans_data;
ALTER TABLE coa_proposal_old RENAME TO coa_proposal;
```
